# Travel Log — 観光地訪問記録アプリ

観光地への「訪問記録」を主役にしたアプリ(仕様書 v0.1 のフェーズ1 MVP)。

- スポットには「種類(観光地・郵便局・御朱印など)」があり、**管理者がアプリ全体の
  対象種類を切り替えられる**(全ユーザーの地図・一覧に反映されるモード切替)
- 観光地には**必訪ランク(S/A/B/C/D)**をキュレーション項目として付与(口コミ評価とは別軸)。
  ランク・カテゴリはスポットの種類ごとに自由(観光地以外は使わなくてもよい)
- 訪問記録(いつ・何回・メモ)をファーストクラスの機能に
- 同一スポットへの複数回訪問に対応
- 観光地モードには全国2,741件のデータを同梱(郵便局・御朱印は種類の枠だけ用意済みで
  データは未収集)

## 技術スタック

| 領域 | 採用技術 |
|---|---|
| フロントエンド | Next.js (App Router) + TypeScript |
| UI | Tailwind CSS |
| 地図 | MapLibre GL JS(OpenStreetMap タイル) |
| バックエンド | Next.js Route Handlers + PostgreSQL(Docker上でローカル完結) |

## 画面

| パス | 内容 |
|---|---|
| `/map` | 地図(ホーム)。ランク別ピン(S/A/B/C/Dの順に大きく・目立つ色に)、訪問済みは✓バッジ。ランク・訪問状態・カテゴリでフィルタ。ピンタップでボトムシート→「詳細を見る」でスポット詳細モーダルへ。トラックパッドの二本指スクロールは移動、Ctrl/⌘+スクロールは拡大縮小 |
| `/spots` | 都道府県→スポット一覧のドリルダウン。ランク順/名前順/訪問日順ソート。行タップでスポット詳細モーダルへ |
| `/admin` | (管理者専用)スポットの種類管理・モード切替、承認待ちキュー・追加・編集・削除・CSVインポート、ユーザー管理 |
| `/login` | メールログイン、または Google でログイン(任意、要設定) |

## セットアップ

アプリ本体・DBともに Docker Compose で起動する(ローカルに Node や Postgres を
インストールする必要はない)。

```bash
docker compose -f docker-compose.dev.yml up --build
```

初回起動時、Postgres コンテナが `db/init/` 配下のSQL(`01_schema.sql`=スキーマ一式、
`02_tourist_spots.sql`=観光地データ2,741件)を自動実行してテーブルを作成する。

http://localhost:3000 を開くと `/login` にリダイレクトされる。初回はアカウントが
存在しないため「アカウントを作成」フォームが表示されるので、メールアドレスと
パスワード(8文字以上)を入力して初回アカウントを作成する
(フェーズ1はこの1アカウントのみで運用する想定)。以降はそのアカウントでログインする。

### Docker を使わない場合

ローカルに Postgres を別途用意し、`.env.example` を `.env.local` としてコピーして
`DATABASE_URL` / `SESSION_SECRET` を設定した上で `npm install && npm run dev` でも
起動できる。その場合は `db/init/01_schema.sql` → `db/init/02_tourist_spots.sql` の順に
手動で実行する。

## Googleログインの設定(任意)

メールログインに加えて、Googleアカウントでのログインも利用できる。設定しない場合は
これまで通りメールログインのみが表示される。

1. [Google Cloud Console](https://console.cloud.google.com/apis/credentials) で
   OAuthクライアントID(種類: ウェブアプリケーション)を作成する
2. 「承認済みのリダイレクトURI」に `http://localhost:3000/api/auth/google/callback`
   を追加する(本番環境ではそのドメインのURLも追加する)
3. 発行された クライアントID / クライアントシークレット を設定する
   - Docker Compose の場合: リポジトリ直下に `.env` ファイルを作成し、
     `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` を書く(`docker compose` が自動で
     読み込む。Next.js が読む `.env.local` とは別物なので注意)
   - Docker を使わない場合: `.env.local` に同じ2つの値を追加する

`users` テーブルはメール+パスワードとGoogleの両方に対応しており、既存のメール
アカウントと同じメールアドレスでGoogleログインした場合は自動的に紐付く。自由な
サインアップはできず、管理者が `/admin` のユーザー管理から作成したアカウントのみ
ログインできる(詳細は次の「権限とスポット承認フロー」参照)。

## 権限とスポット承認フロー

ユーザーには3種類のロールがある。

| ロール | できること |
|---|---|
| 管理者(admin) | スポットの承認・却下・削除、ランク変更を含む編集、ユーザー管理。最初の1アカウント(セットアップ画面で作成した唯一のアカウント)は自動的に管理者になる |
| モデレーター(moderator) | 地図上でのスポット追加(後述、承認待ちとして送信される) |
| 一般ユーザー(user) | 地図・スポット一覧の閲覧、自分の訪問記録の記録のみ(スポット追加は不可) |

新しいアカウントは `/admin` の「ユーザー管理」から管理者が作成し、ロールを割り当てる
(自由サインアップは不可)。Googleログインだけを使わせたい場合も初期パスワードの設定は
必須だが、本人が同じメールアドレスでGoogleログインすれば自動的に連携される。

### 地図からのスポット追加

管理者・モデレーターは `/map` 上で右クリック(モバイルは長押し)するとメニューが出て
「ここにスポットを追加」を選べる。クリックした座標がそのままフォームに入り、送信すると
**必ず「承認待ち」状態になる**(管理者自身の追加も含む)。管理者は `/admin` 上部の
承認待ちキューで個別に承認・却下するか、「すべて承認」で一括公開できる。

`/admin` の既存の追加フォーム・CSVインポートも同じAPIを通るため、同様にすべて承認待ちに
なる点に注意(大量インポート後は「すべて承認」を使うと早い)。新規スポットは常に
「今アクティブなスポットの種類」に紐付けて作成される(下記「スポットの種類」参照)。

## 口コミ・訪問写真

`/spots/[id]` の詳細モーダル内の「訪問を記録」から、訪問記録と同時に以下を残せる。

- **口コミ(公開)**: 星評価などのスコアはなく、本文のみのシンプルなテキスト口コミ。
  他ユーザーにも公開され、スポット詳細モーダルに一覧表示される。ロールに関わらず
  全ログインユーザーが投稿可能。スポット1件につきユーザー1人1件(再度投稿すると上書き)
- **写真(非公開)**: 自分の訪問記録にのみ添付され、他ユーザーには見えない。選択した画像は
  ブラウザ側で縮小・JPEG圧縮した上でサーバーに送られ、リポジトリ直下の `photos/`
  フォルダ(Docker では bind マウント)にファイルとして保存される。DB の
  `visits.photos`列(text[])にはフォルダ内の相対パスだけが入る
  (詳細は下記「写真の保存先とデータ移行」)

## 写真の保存先とデータ移行

訪問写真は `photos/<ユーザーID>/<年>/<月>/<uuid>.jpg` に保存される(`lib/photos.ts`)。
ユーザー×年月でサブフォルダに振り分けるため、1フォルダに大量のファイルが溜まって
一覧表示が重くなることがない。配信は認証付きの `/api/photos/...` 経由で、
本人以外はアクセスできない(写真は非公開のため)。

- `photos/` フォルダは `.gitkeep` だけをコミットしてあり、中身は `.gitignore` 対象
  (実際の写真=個人情報をコミットしないため)。clone した時点でフォルダが存在するので、
  マウント先を自動作成しない環境(Synology Container Manager 等)でもそのまま起動できる
- 本番用 `docker-compose.yml` は `./photos` をコンテナの `/app/photos` に bind マウント
  する。開発用 `docker-compose.dev.yml` はリポジトリ全体を `/app` にマウントするため
  追加設定は不要。Docker を使わない場合は環境変数 `PHOTOS_DIR` で保存先を変えられる
  (既定はカレントディレクトリ直下の `photos`)

### 旧方式(DB直接保存)からの移行

以前は写真を Base64 文字列として `visits.photos` に直接保存していた。旧データが
残っていても表示はそのまま動くが(`data:` で始まる値はそのまま表示される)、DB が
肥大化したままになるので、`scripts/migrate-photos-to-files.mjs` でファイルへ移行できる
(data URL の要素だけを変換するため何度実行しても安全)。

```bash
# 開発環境(docker-compose.dev.yml)の場合
docker compose -f docker-compose.dev.yml exec app node scripts/migrate-photos-to-files.mjs

# 本番環境(docker-compose.yml)の場合: scriptsフォルダだけを一時的にマウントして実行
docker compose run --rm -v ./scripts:/app/scripts app node scripts/migrate-photos-to-files.mjs
```

移行後は `vacuum full visits;` を実行すると DB ファイルの肥大が実際に解消される。

## スポットの種類とモード切替

スポットは `spot_types`(観光地/郵便局/御朱印など)に属し、`app_settings` が
「今アプリ全体でどの種類を対象にするか」を1つだけ保持する。`/admin` の
「スポットの種類」セクションで管理者が切り替えると、`/map`・`/spots`・スポット追加は
即座にその種類だけを対象にする(他の種類のデータは隠れるだけで消えない)。

初期状態では `tourist`(観光地・データ2,741件あり)/ `post_office`(郵便局)/
`goshuin`(御朱印)の3種類が用意されており、`tourist` がアクティブ。後者2つは
枠だけでデータは未収集。管理者は同じ画面から新しい種類(キー+表示名)を追加できる。

## CSVインポート形式

`/admin` からインポートできる。1行目はヘッダー行(列順は自由)。

```csv
name,name_kana,prefecture,municipality,lat,lng,rank,category,description,official_url
厳島神社,いつくしまじんじゃ,広島県,廿日市市,34.2959,132.3197,S,神社仏閣,海に浮かぶ大鳥居,https://example.com
```

- 必須列: `name`, `prefecture`, `lat`, `lng`
- `rank`/`category` は自由入力(空でも可)。スポットの種類ごとに意味が異なってよく、
  DB側で値を制約していない。観光地(`tourist`)は下記「ランクの決め方」の基準を使う
- インポートしたスポットは常に「今アクティブなスポットの種類」に紐付く

## ランクの決め方(観光地)

観光地(`tourist`)の必訪ランクは主観ではなく、**Wikipedia(ja)の月次ページビュー数**を
知名度の客観指標としてパーセンタイル区分している(観光地2,741件中の相対順位)。
他のスポットの種類は独自のランク基準を使うか、ランクを使わなくてもよい。

データの大半(2,585件)は Overpass API(OpenStreetMap)で全都道府県から
`tourism`/`historic`/`natural`/神社仏閣タグ等を一括取得し、Wikipedia記事が存在するもの
だけを候補として絞り込んだ上で、そのページビュー数を取得して機械的にランク付けしている
(取得・ランク付けスクリプトはリポジトリに含めていない一時作業)。OSMのタグ付けは有志による
ものなので、`category`列は`tourism=museum`→`美術館博物館`のような簡易マッピングによる
機械的な割り当てであり、精度にはばらつきがある。

| ランク | 相対順位 | 目安 |
|---|---|---|
| S | 上位5% | 全国的に絶対外せない |
| A | 次15% | 全国区で有名 |
| B | 次30% | 地方の定番 |
| C | 次30% | 地元で知られている |
| D | 残り20% | 穴場・マニアック向け |

世界遺産・国宝等の指定があるがページビューが伸びにくい場所は、目視で格上げする例外を
許容するハイブリッド方式(完全自動ではない)。手動でスポットを追加する場合も、この基準を
参考にランクを付けるとブレにくい。

## データ設計

`spot_types`(スポットの種類マスタ)/ `app_settings`(今アクティブな種類を1行だけ保持)/
`spots`(スポットマスタ。`spot_type_id`で種類を持つ)/ `visits`(訪問記録・写真は非公開)/
`reviews`(口コミ・公開、スポット1件につき1ユーザー1件)/ `users`(ログイン用アカウント)
を分離。必訪ランクは spots 側のキュレーション項目で、reviews には一切依存しない。

アクセス制御は Supabase RLS の代わりに Next.js の Route Handlers(`app/api/**`)側で行う。
署名付きセッションCookie(`lib/auth/session.ts`)でログイン中のユーザーを識別し、
`visits`/`reviews` は常にログイン中のユーザーIDに紐付けてサーバー側で読み書きする。
