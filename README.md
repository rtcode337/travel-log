# Travel Log — 観光地訪問記録アプリ

観光地への「訪問記録」を主役にしたアプリ(仕様書 v0.1 のフェーズ1 MVP)。

- スポットには「種類(観光地・郵便局・御朱印)」があり、各種類ごとに独立したURL
  (`/tourist/map`のように`/[種類キー]/...`)を持つ。管理者は種類ごとに公開範囲
  (全員に公開/管理者のみ/無効)を設定でき、ログイン後の既定の遷移先(1種類)も選べる
- 観光地には**必訪ランク(A/B/C/D/E)**をキュレーション項目として付与(口コミ評価とは別軸)。
  ランク・カテゴリはスポットの種類ごとに自由(観光地以外は使わなくてもよい)
- 訪問記録(いつ・何回・メモ)をファーストクラスの機能に
- 同一スポットへの複数回訪問に対応
- 「訪問予定」(行きたい場所のブックマーク)にも対応。訪問を記録すると自動的に外れる
- 観光地・郵便局・御朱印の3種類ともデータを同梱(観光地7,050件、郵便局24,526件、
  御朱印46,574件、計78,150件。詳細は下記「スポットの種類とデータ量」参照)

## 技術スタック

| 領域 | 採用技術 |
|---|---|
| フロントエンド | Next.js (App Router) + TypeScript |
| UI | Tailwind CSS |
| 地図 | MapLibre GL JS(OpenStreetMap タイル) |
| バックエンド | Next.js Route Handlers + PostgreSQL(Docker上でローカル完結) |

## 画面

すべて`/[種類キー]/...`の形式(例: `/tourist/map`)。`種類キー`は`spot_types.key`
(`tourist`/`post_office`/`goshuin`など)で、同じ画面をスポットの種類ごとに切り替えて使う。
ルートパス`/`は`app_settings`が保持する既定の種類の`/map`へ自動リダイレクトされる。

| パス | 内容 |
|---|---|
| `/[type]/map` | 地図(ホーム)。ランク別ピン(A〜Eの順に大きく・目立つ色に)、訪問済みは✓バッジ。ランク・訪問状態・カテゴリでフィルタ。ピンタップでボトムシート→「詳細を見る」でスポット詳細モーダルへ。トラックパッドの二本指スクロールは移動、Ctrl/⌘+スクロールは拡大縮小 |
| `/[type]/spots` | 「都道府県から探す」(都道府県→スポット一覧のドリルダウン)と「ランクから探す」(名前・都道府県での検索+ランク絞り込み+ページング、100件単位)の2タブ。行タップでスポット詳細モーダルへ |
| `/[type]/admin` | (管理者・スポット管理者専用)スポットの承認待ちキュー・追加・編集・削除・CSVインポート・SQLシードとの同期。加えてadminのみ、スポットの種類の追加・公開範囲設定・既定の種類の変更、ユーザー管理ができる |
| `/[type]/account` | 自分のロール・現在の種類の表示、ログアウト、他のスポットの種類への切り替えリンク |
| `/login` | メールログイン、または Google でログイン(任意、要設定) |

## セットアップ

アプリ本体・DBともに Docker Compose で起動する(ローカルに Node や Postgres を
インストールする必要はない)。

```bash
docker compose -f docker-compose.dev.yml up --build
```

初回起動時、Postgres コンテナが `db/init/` 配下のSQL(`01_schema.sql`=スキーマ一式、
`02_tourist_spots_by_prefecture.sh`=`tourist_by_prefecture/`配下の観光地データ(都道府県別ファイル)を
順に読み込むラッパー、
`03_post_offices.sql`=郵便局データ、`03_goshuin_spots.sql`+`04_goshuin_unranked_z.sql`=
御朱印データ)を自動実行してテーブルを作成する。

http://localhost:3000 を開くと `/login` にリダイレクトされる。初回はアカウントが
存在しないため「アカウントを作成」フォームが表示されるので、メールアドレスと
パスワード(8文字以上)を入力して初回アカウントを作成する
(フェーズ1はこの1アカウントのみで運用する想定)。以降はそのアカウントでログインする。

### Docker を使わない場合

ローカルに Postgres を別途用意し、`.env.example` を `.env.local` としてコピーして
`DATABASE_URL` / `SESSION_SECRET` を設定した上で `npm install && npm run dev` でも
起動できる。その場合は `db/init/` 配下のSQL(`tourist_by_prefecture/*.sql`を含む)を
ファイル名の順(`01_`→`02_`→`03_`→`04_`)に手動で実行する。

## Googleログインの設定(任意)

メールログインに加えて、Googleアカウントでのログインも利用できる。設定しない場合は
これまで通りメールログインのみが表示される。

1. [Google Cloud Console](https://console.cloud.google.com/apis/credentials) で
   OAuthクライアントID(種類: ウェブアプリケーション)を作成する
2. 「承認済みのリダイレクトURI」に `http://localhost:3000/api/auth/google/callback`
   を追加する(本番環境ではそのドメインのURLも追加する)
3. 発行された クライアントID / クライアントシークレット を設定する
   - Docker Compose の場合: リポジトリ直下に `.env` ファイルを作成し、
     `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` を書く(`docker compose` が自動で
     読み込む。Next.js が読む `.env.local` とは別物なので注意)
   - Docker を使わない場合: `.env.local` に同じ2つの値を追加する

`users` テーブルはメール+パスワードとGoogleの両方に対応しており、既存のメール
アカウントと同じメールアドレスでGoogleログインした場合は自動的に紐付く。自由な
サインアップはできず、管理者が `/[type]/admin` のユーザー管理から作成したアカウントのみ
ログインできる(詳細は次の「権限とスポット承認フロー」参照)。

## 権限とスポット承認フロー

ユーザーには4種類のロールがある。

| ロール | できること |
|---|---|
| 管理者(admin) | スポットの承認・却下・削除、ランク変更を含む編集、公開スポットの直接作成、スポットの種類の追加・公開範囲設定、ユーザー管理。最初の1アカウント(セットアップ画面で作成した唯一のアカウント)は自動的に管理者になる |
| スポット管理者(spot_admin) | スポットに関してはadminと同じ権限(承認・却下・削除、公開スポットの直接作成・編集)。スポットの種類設定・ユーザー管理はできない |
| モデレーター(moderator) | 地図上でのスポット追加(非公開または承認待ちとして送信される)。承認待ちキューの閲覧はできるが承認・却下はできない |
| 一般ユーザー(user) | 地図・スポット一覧の閲覧、自分の訪問記録・訪問予定の管理、非公開スポットの追加のみ(承認待ち・公開状態での追加は不可) |

新しいアカウントは `/[type]/admin` の「ユーザー管理」(admin専用)から作成し、ロールを割り当てる
(自由サインアップは不可)。Googleログインだけを使わせたい場合も初期パスワードの設定は
必須だが、本人が同じメールアドレスでGoogleログインすれば自動的に連携される。

### 地図からのスポット追加

`/[type]/map` 上で右クリック(モバイルは長押し)するとメニューが出て「ここにスポットを追加」を
選べる。クリックした座標がそのままフォームに入り、送信時のstatusの既定値はロールにより異なる
(`user`は`private`=非公開、それ以外は`pending`=承認待ち)。admin/spot_adminはフォーム上で
`published`(公開)を直接選ぶこともできる。admin/spot_adminは `/[type]/admin` 上部の
承認待ちキューで個別に承認・却下するか、「すべて承認」で一括公開できる。

`/[type]/admin` の既存の追加フォーム・CSVインポートも同じAPIを通るため、同様のロール別
既定値が適用される点に注意(大量インポート後は「すべて承認」を使うと早い)。新規スポットは
常に今開いている種類(URLの`[type]`)に紐付けて作成される。

## 訪問予定・口コミ・訪問写真

`/[type]/spots`の各スポット詳細モーダルから、以下を管理できる。

- **訪問予定(非公開)**: 「行きたい場所」のブックマーク。詳細モーダルからトグルで追加・解除でき、
  トップ画面(`/[type]/spots`)に一覧表示される。該当スポットの訪問を記録すると自動的に外れる
- **口コミ(公開)**: 星評価などのスコアはなく、本文のみのシンプルなテキスト口コミ。
  他ユーザーにも公開され、スポット詳細モーダルに一覧表示される。ロールに関わらず
  全ログインユーザーが投稿可能。スポット1件につきユーザー1人1件(再度投稿すると上書き)
- **写真(非公開)**: 自分の訪問記録にのみ添付され、他ユーザーには見えない。選択した画像は
  ブラウザ側で縮小・JPEG圧縮した上でサーバーに送られ、リポジトリ直下の `photos/`
  フォルダ(Docker では bind マウント)にファイルとして保存される。DB の
  `visits.photos`列(text[])にはフォルダ内の相対パスだけが入る
  (詳細は下記「写真の保存先とデータ移行」)

スポット詳細モーダルには、Wikipedia(ja)からスポット名で検索して概要を表示する機能もある。
名前単体で検索し、複数の候補や曖昧さ回避ページに当たった場合はスポットの所在地(市区町村→
都道府県)が一致するものを自動選択する。同名の別の場所の情報が出ることがある旨はUI上に注記される。

## 写真の保存先とデータ移行

訪問写真は `photos/<ユーザーID>/<年>/<月>/<uuid>.jpg` に保存される(`lib/photos.ts`)。
ユーザー×年月でサブフォルダに振り分けるため、1フォルダに大量のファイルが溜まって
一覧表示が重くなることがない。配信は認証付きの `/api/photos/...` 経由で、
本人以外はアクセスできない(写真は非公開のため)。

- `photos/` フォルダは `.gitkeep` だけをコミットしてあり、中身は `.gitignore` 対象
  (実際の写真=個人情報をコミットしないため)。clone した時点でフォルダが存在するので、
  マウント先を自動作成しない環境(Synology Container Manager 等)でもそのまま起動できる
- 本番用 `docker-compose.yml` は `./photos` をコンテナの `/app/photos` に bind マウント
  する。開発用 `docker-compose.dev.yml` はリポジトリ全体を `/app` にマウントするため
  追加設定は不要。Docker を使わない場合は環境変数 `PHOTOS_DIR` で保存先を変えられる
  (既定はカレントディレクトリ直下の `photos`)

### 旧方式(DB直接保存)からの移行

以前は写真を Base64 文字列として `visits.photos` に直接保存していた。旧データが
残っていても表示はそのまま動くが(`data:` で始まる値はそのまま表示される)、DB が
肥大化したままになるので、`scripts/migrate-photos-to-files.mjs` でファイルへ移行できる
(data URL の要素だけを変換するため何度実行しても安全)。

```bash
# 開発環境(docker-compose.dev.yml)の場合
docker compose -f docker-compose.dev.yml exec app node scripts/migrate-photos-to-files.mjs

# 本番環境(docker-compose.yml)の場合: scriptsフォルダだけを一時的にマウントして実行
docker compose run --rm -v ./scripts:/app/scripts app node scripts/migrate-photos-to-files.mjs
```

移行後は `vacuum full visits;` を実行すると DB ファイルの肥大が実際に解消される。

## スポットの種類とデータ量

スポットは `spot_types`(観光地/郵便局/御朱印)に属し、種類ごとに独立したURL
(`/[key]/map`等)を持つ。`spot_types.visibility`で公開範囲を設定できる
(`public`=全員に公開/`admin_only`=admin・spot_adminのみ閲覧可(公開前の準備用)/
`disabled`=全員に対して404・非表示。ただし`/[key]/admin`自体は再有効化のため常にアクセス可)。
`app_settings`は「ログイン後・ルートパス`/`アクセス時にどの種類へリダイレクトするか」の
既定値を1つだけ保持し、`/[type]/admin`から管理者が変更できる。ユーザーは`/[type]/account`の
「別のスポットを見る」リンクから、公開範囲が許す他の種類にいつでも切り替えられる。
管理者は同じ画面から新しい種類(キー+表示名)を追加できる。

| 種類キー | 表示名 | 件数 | データソース・ランク基準 |
|---|---|---|---|
| `tourist` | 観光地 | 7,050件 | Wikipedia(ja)月次ページビュー数によるA〜E区分(詳細は次節)。都道府県別に`db/init/tourist_by_prefecture/`配下のファイルに分割 |
| `post_office` | 郵便局 | 24,526件 | 国土数値情報(郵便局データ P30)。rankは知名度順位ではなく地図表示用の固定値`郵便局` |
| `goshuin` | 御朱印 | 46,574件 | OSM Overpass由来の寺社。Wikipedia記事があるもの6,584件はA〜E区分、記事がないもの39,990件は`Z`(未整理)固定 |

## CSVインポート形式

`/[type]/admin` からインポートできる。1行目はヘッダー行(列順は自由)。

```csv
name,name_kana,prefecture,municipality,lat,lng,rank,category,description,official_url
厳島神社,いつくしまじんじゃ,広島県,廿日市市,34.2959,132.3197,A,神社仏閣,海に浮かぶ大鳥居,https://example.com
```

- 必須列: `name`, `prefecture`, `lat`, `lng`
- `rank`/`category` は自由入力(空でも可)。スポットの種類ごとに意味が異なってよく、
  DB側で値を制約していない。観光地(`tourist`)は下記「ランクの決め方」の基準を使う
- インポートしたスポットは常に今開いている種類(URLの`[type]`)に紐付く

## SQLシードとの同期

`/[type]/admin`の「SQLシードとの同期」から、`db/init/`配下のその種類のシードファイル
(`insert into spots ... where t.key = '<種類>';`形式)を読み、
`name`+`prefecture`+`municipality`が完全一致するスポットがまだテーブルに存在しない行だけを
公開状態で追加できる。db/initの新規・変更ファイルを手動で`psql`適用する代わりに使える
(ただし表記ゆれや座標近接による重複はこの完全一致判定では検出しないため、取り込み後は
CLAUDE.mdの注意書き通り目視で重複確認すること)。本番用Dockerイメージ(`next build`の
standalone出力)にもこの機能のために`db/init`を同梱している(`Dockerfile`参照)。

## ランクの決め方(観光地)

観光地(`tourist`)の必訪ランクは主観ではなく、**Wikipedia(ja)の月次ページビュー数**を
知名度の客観指標としてパーセンタイル区分している(観光地7,050件中の相対順位)。
他のスポットの種類は独自のランク基準を使うか、ランクを使わなくてもよい(上記
「スポットの種類とデータ量」参照)。最上位をSにすると運用上何かと面倒なため、A〜Eの
5段階にしている。

データの大半(2,585件)は Overpass API(OpenStreetMap)で全都道府県から
`tourism`/`historic`/`natural`/神社仏閣タグ等を一括取得し、Wikipedia記事が存在するもの
だけを候補として絞り込んだ上で、そのページビュー数を取得して機械的にランク付けしている
(取得・ランク付けスクリプトはリポジトリに含めていない一時作業)。OSMのタグ付けは有志による
ものなので、`category`列は`tourism=museum`→`美術館博物館`のような簡易マッピングによる
機械的な割り当てであり、精度にはばらつきがある。

| ランク | 相対順位 | 目安 |
|---|---|---|
| A | 上位5% | 全国的に絶対外せない |
| B | 次15% | 全国区で有名 |
| C | 次30% | 地方の定番 |
| D | 次30% | 地元で知られている |
| E | 残り20% | 穴場・マニアック向け |

世界遺産・国宝等の指定があるがページビューが伸びにくい場所は、目視で格上げする例外を
許容するハイブリッド方式(完全自動ではない)。手動でスポットを追加する場合も、この基準を
参考にランクを付けるとブレにくい。

## データ設計

`spot_types`(スポットの種類マスタ。公開範囲`visibility`を持つ)/
`app_settings`(ログイン後・`/`アクセス時の既定の種類を1行だけ保持)/
`spots`(スポットマスタ。`spot_type_id`で種類を持つ)/ `visits`(訪問記録・写真は非公開)/
`visit_plans`(訪問予定・非公開・訪問記録作成時に自動削除)/
`reviews`(口コミ・公開、スポット1件につき1ユーザー1件)/ `users`(ログイン用アカウント、
ロールは`lib/types.ts`の`Role`参照)を分離。必訪ランクは spots 側のキュレーション項目で、
reviews には一切依存しない。

アクセス制御は Supabase RLS の代わりに Next.js の Route Handlers(`app/api/**`)側で行う。
署名付きセッションCookie(`lib/auth/session.ts`)でログイン中のユーザーを識別し、
`visits`/`visit_plans`/`reviews` は常にログイン中のユーザーIDに紐付けてサーバー側で読み書きする。
